A. PROFESSIONAL PORTRAIT ID CARD DESIGN — REQUIRED LAYOUT
The ID card MUST be PORTRAIT (vertical), not landscape. Use a clean, print-ready, professional corporate/industrial design with strong contrast, readable typography, proper spacing, and a compact scannable barcode. Prefer a standard CR80 card rotated to portrait orientation (approximately 54 × 85.6 mm) unless the existing printer or project requirements specify another size.

Exact layout rules:
1. ABB logo at the TOP, centered or aligned neatly.
2. Below the logo, show the person category as one prominent centered title ONLY:
   "WORKER" or "INTERN" or "VISITOR".
   Do NOT add a separate label like "CATEGORY" above it. For example, show "WORKER" centered in the middle of the header area, not "CATEGORY: WORKER".
3. Person's photo centered below the category title, if available and appropriate.
4. Full name, clearly readable.
5. Short unique ID number, such as W101, I101, or V101.
6. A compact but reliably scannable 1D barcode below the ID number (or in the lower section).
7. Valid-until date clearly displayed near the bottom, e.g. "VALID UNTIL: 18 OCT 2027".
8. Optional small "ABB PLANT 3" footer if consistent with approved branding.
9. Keep all elements aligned on a single vertical card canvas. Do not accidentally use a horizontal card layout at screen or print time.
10. No extra category label anywhere on the card; the category word itself (WORKER/INTERN/VISITOR) is enough.

Suggested vertical order:
[ABB LOGO]
[WORKER / INTERN / VISITOR — centered]
[PERSON PHOTO]
[FULL NAME]
[ID NO. W101 / I101 / V101]
[1D BARCODE]
[VALID UNTIL: DD MMM YYYY]
[ABB PLANT 3 — optional footer]

ID numbering:
- Worker: W101, W102, W103...
- Intern: I101, I102, I103...
- Visitor: V101, V102, V103... (confirm this proposed prefix with the project owner).
- Group visitor passes should have a distinct group-pass reference, not pretend to be an individually assigned person's ID.
- Generate IDs on the backend with database-level uniqueness and concurrency protection. Do not generate IDs only in the browser. Never reuse an ID after archival.
- Keep the human-facing short ID separate from the internal database primary key. An internal UUID/identity key is acceptable; users should see the short readable ID on the card and UI.

Barcode rules:
- Use a compact 1D barcode format such as Code 128 if compatible with the chosen scanner library and physical scanning devices.
- Encode only the short unique ID or a non-sensitive opaque credential reference. Never encode passwords, Aadhaar/PAN data, phone numbers, or other personal details.
- Keep enough barcode width/height and quiet-zone/margins for reliable scanning; do not shrink it merely to make the card look attractive.
- Render at print-friendly resolution/size. Provide a print preview and test scanning from a printed card and a screen at different distances/angles.
- Do not claim universal scanning range. Test with available scanners and document practical limitations.
- If credentials can be revoked/reissued, barcode scans must still be validated by the backend; the barcode alone is not proof of validity.

Card output:
- Use browser print styling that hides navigation, buttons, and unrelated page content.
- Keep the front design simple and readable. Put sensitive ID-proof documents on the secure record screen, NOT on the printed ID card.
- Do not print Aadhaar/PAN images or numbers on the ID card.
- If a back side is implemented, include only approved non-sensitive instructions/contact details. Do not invent company policy.
- Add a preview before print/download and test alignment, scaling, and barcode legibility.

D. GATE SCAN / VERIFY PAGE
Make the gate screen simple and suitable for security staff using a desktop, laptop, or phone. It should show only:
1. Scan input/camera control.
2. Clear verification result.
3. Person details.
4. Latest gate events/logs.
5. Authorized manual IN/OUT controls.

Scanning methods:
- USB barcode scanner.
- Bluetooth scanner paired with a laptop or phone.
- Keyboard-wedge scanner input (many scanners type the scanned value and press Enter).
- Phone camera or laptop webcam when supported by the browser/device.
- Use a maintained barcode decoder that supports the chosen 1D barcode format.
- Ask for camera permission and handle denied permission, missing camera, poor lighting, and unsupported devices gracefully.
- Do not claim every Bluetooth scanner can connect directly through a browser. Support keyboard-wedge input when available and document tested hardware/browser combinations.

On successful or rejected scan, show:
- Person's photo if available.
- Short ID, full name, category, validity, and current gate state.
- Contractor or institute details if applicable and authorized.
- Visitor host/reason when applicable.
- A secure button/link to open the person's record and approved ID-proof images when the operator's role permits it.

Corner confirmation:
- After every scan attempt, show a small, non-blocking toast/notification in a screen corner.
- Success example: "ENTRY RECORDED — W101".
- Exit example: "EXIT RECORDED — W101".
- Canteen duplicate example: "ALREADY USED TODAY — W101".
- Rejected example: "ACCESS DENIED — CARD EXPIRED".
- Service failure example: "UNABLE TO VERIFY — TRY AGAIN".
- Use accessible contrast and clear status text/icons; do not rely on color alone.
- The toast should not cover the scan input or essential person details and should dismiss automatically while the result remains visible long enough for security staff to read.
- Prevent a single physical scan from creating multiple requests due to repeated camera frames, Enter events, or duplicate callbacks.

Verification outcomes:
- APPROVED only after the backend successfully validates the credential and action.
- REJECTED for invalid, expired, revoked, not-yet-valid, or policy-disallowed access.
- UNABLE TO VERIFY if the authoritative backend/database cannot be reached.
- Never approve offline just because a barcode can be decoded.

E. AUTOMATIC GATE IN/OUT
- Determine the next accepted gate action from the latest successful gate state for the person/card:
  * Current state OUT → next accepted scan records IN.
  * Current state IN → next accepted scan records OUT.
- A single physical scan must create exactly one gate event.
- Add duplicate-request/idempotency protection and a sensible configurable debounce/cooldown.
- Do not suppress legitimate later scans forever.
- Use database transactions/locking or equivalent concurrency-safe logic so simultaneous scans at multiple gates cannot corrupt state.
- Keep historical events immutable. Do not rewrite old records to hide errors.
- Provide a manual IN/OUT override for authorized security staff when the automatic state is wrong. Require a reason and record the operator, timestamp, previous state, new state, and reason in the audit log.
- Do not let a manual override bypass credential validity unless the approved site policy explicitly permits it.
- Do not automatically reset everyone to OUT at midnight. Ask about overnight/shift policy if it affects the logic.

F. CANTEEN PAGE — ONE SUCCESSFUL ENTRY PER LOCAL DAY
- Simplify to scan input/camera control, person details, latest logs, and a corner confirmation toast.
- Use the same barcode input methods as the gate page where supported.
- A card/person may have only one successful canteen entry per Plant 3 local calendar day.
- A second scan that day must show "ALREADY USED TODAY" and must not create a second successful entry.
- Enforce this in backend logic and PostgreSQL with a concurrency-safe unique constraint/design. Frontend-only checks are insufficient.
- Store timestamp, person/credential reference, local service date, result, and operator/device where available.
- Define the timezone and local-day boundary with the project owner; do not silently assume UTC is the canteen's day.
- Test simultaneous scans at multiple counters.
